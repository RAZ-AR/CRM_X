# СОЗДАЙ WEB-СЕРВИС УПРАВЛЕНИЯ ПРОЕКТОМ

Создай полноценный современный web-сервис для управления запуском и операционной работой многофункционального пространства.

Сервис должен быть **полностью самостоятельным продуктом**, без зависимости от Notion, Airtable и других подобных систем.

Главная цель:

> **Сотрудник должен сразу понимать, что ему делать.  
> CPO / Owner должен сразу понимать, что происходит с проектом.**

Не делай сложную корпоративную ERP. Нужен простой, быстрый, красивый и понятный интерфейс.

---

# 1. ОСНОВНАЯ РОЛЬ

В системе есть одна главная управляющая роль:

## 👑 CPO / OWNER

Это одна и та же роль.

CPO / Owner полностью управляет проектом:

- создаёт и изменяет структуру проекта;
- создаёт этапы;
- создаёт зоны;
- создаёт направления работ;
- создаёт и назначает задачи;
- назначает сотрудников;
- устанавливает сроки;
- устанавливает приоритеты;
- управляет Roadmap;
- управляет пользователями;
- назначает роли и права;
- видит все задачи;
- видит прогресс проекта;
- видит прогресс каждой зоны;
- видит просрочки;
- видит заблокированные задачи;
- видит Critical Path;
- контролирует готовность зон к открытию.

CPO / Owner имеет полный доступ.

---

# 2. СОТРУДНИК

Сотрудник получает логин и пароль.

После входа он попадает в свой персональный интерфейс.

## Главное правило доступа

По умолчанию сотрудник видит **только информацию, необходимую ему для работы**.

Если сотруднику информация не нужна для выполнения работы — он её не видит.

## Три уровня доступа

Права **не должны быть жёстко привязаны только к роли**.

### 👑 CPO / Owner

Роль. Видит и управляет всем.

### 👤 Employee

Роль. Базовые права: свои задачи + то, что явно разрешено.

### 🔐 Permission

Дополнительные права, которые выдаёт CPO поверх роли.

CPO может открыть конкретный раздел или зону, не меняя роль человека.

Примеры:

> Иван — сотрудник Corner, но разрешить ему видеть весь Corner Roadmap.

> Маркетолог — сотрудник, но ему разрешить видеть Marketing во всех зонах.

То есть:

**Роль = базовые права**  
**Доступ = дополнительные права, которые выдаёт CPO**

Это даёт простую систему сейчас и не загоняет продукт в жёсткие рамки позже.

---

## Что видит сотрудник по умолчанию

### 1. 🏠 Главный экран (Home)

Только своя рабочая картина:

- свои задачи;
- задачи на сегодня;
- ближайшие дедлайны;
- просроченные свои задачи;
- задачи, которые он создал;
- уведомления;
- свой текущий прогресс.

Никаких сложных графиков, финансов и общей картины проекта.

### 2. ✅ Мои задачи

Полный список задач, где он:

- ответственный;
- автор;
- участник задачи.

Может:

- открыть задачу;
- изменить статус;
- добавить комментарий;
- прикрепить файл;
- добавить результат;
- изменить / добавить детали только в пределах разрешённых полей.

Не может менять чужие задачи, Critical Path, зависимости, управленческие поля.

### 3. ➕ Создание задачи

Может создать задачу самостоятельно.

При создании доступны поля:

- название;
- описание;
- зона;
- срок;
- приоритет;
- комментарий;
- файл.

По умолчанию задача назначается ему самому.

Автор = этот сотрудник.  
Ответственный = этот сотрудник (пока CPO не переназначит).

**Важно:** сотрудник не может через создание задачи получить доступ к закрытой информации проекта. Создание задачи не открывает Dashboard, бюджет, чужие зоны, Roadmap, Critical Path и т.п.

### 4. 🏢 Своя зона

Сотрудник может видеть свою рабочую зону **только если CPO дал такое право**.

Например, сотрудник Corner при разрешении видит:

🧇 Corner

- общий прогресс зоны;
- мои задачи;
- задачи команды Corner;
- ближайшие работы;
- что сейчас происходит в зоне.

Но **не видит** внутреннюю информацию других зон.

Без permission раздел зоны сотруднику не показывается.

### 5. 👥 Команда своей зоны

Если разрешено CPO:

- сотрудники своей зоны;
- их рабочие задачи;
- статус задач.

Не зарплаты, личные данные, контакты сверх рабочих, административную информацию, нагрузку в управленческом смысле.

### 6. 📎 Материалы своих задач

Может видеть файлы и комментарии тех задач, к которым у него есть доступ (ответственный, автор, участник).

Не видит файлы закрытых управленческих документов, даже если они лежат в той же зоне.

---

## Что сотрудник НЕ видит по умолчанию

- ❌ полный Dashboard проекта;
- ❌ финансовые показатели;
- ❌ бюджет;
- ❌ зарплаты;
- ❌ закупочные цены / стоимость закупок и оборудования;
- ❌ весь Roadmap проекта;
- ❌ Critical Path проекта;
- ❌ задачи других зон;
- ❌ внутренние управленческие решения;
- ❌ настройки проекта;
- ❌ роли и права пользователей;
- ❌ управление сотрудниками;
- ❌ общий процент проекта;
- ❌ закрытые управленческие документы;
- ❌ найм (кроме своих задач, если он назначен ответственным);
- ❌ закупки и оборудование как отдельные разделы (цены, поставщики, статусы закупок скрыты, если нет permission).

Сотрудник НЕ может:

- менять структуру проекта;
- менять этапы;
- менять Roadmap;
- управлять пользователями;
- назначать роли и выдавать permissions;
- менять системные настройки;
- удалять чужие задачи;
- изменять управленческую структуру проекта;
- видеть и править поля стоимости, зарплат, бюджета.

---

## Permissions, которые CPO может выдать сотруднику

Каждый permission — отдельный тумблер / набор, не новая роль.

Примеры грантов:

- видеть свою зону (страница зоны без финансов);
- видеть задачи команды своей зоны;
- видеть команду своей зоны (имена, должности, статусы задач);
- видеть Roadmap своей зоны;
- видеть Marketing по всем зонам;
- видеть Readiness своей зоны (без управленческих комментариев);
- видеть конкретный раздел (например только Equipment своей зоны, без цен);
- быть участником задач вне своей зоны — тогда видит только эти задачи.

Грант всегда минимальный: открывается конкретный раздел / зона / тип данных, а не «всё подряд».

На уровне данных (RLS / API) доступ проверяется так же, как в UI. Скрыть пункт меню недостаточно.

Сделать:

При создании пользователя CPO / Owner назначает:

- имя;

- 👑 CPO / Owner
- 👤 Employee

Не усложнять RBAC без необходимости.

Не делать права жёстко привязанными только к роли. Роль даёт базу. CPO выдаёт дополнительные Permission на раздел или зону.

# 7. СОЗДАНИЕ ЗАДАЧИ

CPO может создать задачу и назначить её сотруднику.

Пример:

> Купить вафельницу  
> Зона: Corner  
> Ответственный: Иван  
> Срок: 18 сентября  
> Приоритет: Высокий

Сотрудник также может создать задачу сам.

Например:

> Купить упаковку для вафель

При создании сотрудником:

- автор = этот сотрудник;
- ответственный = этот сотрудник;
- задача появляется у CPO;
- задача входит в общий прогресс;
- сотрудник может позже изменить её статус.

CPO должен видеть все задачи, включая созданные сотрудниками.

Для CPO:

**Все задачи**

- зона;
- сотрудник;
- этап;
- приоритет;
- статус;
- просрочка;

# 9. ROADMAP

Создать красивый визуальный Roadmap проекта.

Это один из главных экранов системы.

Основные этапы:

`🚀 START`

`🎨 DESIGN`

`🏗️ BUILD`

`🛠️ EQUIPMENT`

`👥 TEAM`

`📋 OPERATIONS`

`💻 IT`

`📣 MARKETING`

`🧪 TEST`

`🚪 OPEN`

`📈 POST-LAUNCH`

Этапы могут выполняться параллельно.

Roadmap должен показывать:

- даты;
- продолжительность;
- задачи;
- зоны;
- milestones;
- прогресс;
- критические задачи;
- зависимости;
- даты открытия.

Roadmap должен выглядеть как современный продуктовый / startup project roadmap, а не как старая корпоративная таблица.

По умолчанию сотрудник **не видит** весь Roadmap проекта.

CPO может отдельным permission открыть сотруднику Roadmap своей зоны или конкретное направление (например Marketing).

CPO / Owner может:

- создавать этапы;
- изменять даты;
- менять порядок;
- добавлять milestones;
- менять задачи;
- управлять зависимостями;
- выдавать сотрудникам доступ к Roadmap / зоне / разделу.

Система должна автоматически показывать последствия изменения сроков.

Но окончательное решение об официальной дате открытия принимает CPO / Owner.

Очень важный раздел.

Для каждой зоны рассчитывать готовность по блокам:

`SPACE`

`EQUIPMENT`

`TEAM`

`PRODUCT`

`IT`

`MARKETING`

`OPERATIONS`

`READY`

Например:

### 🧇 Corner

**87%**

SPACE 🟢  
EQUIPMENT 🟡  
TEAM 🟢  
PRODUCT 🟢  
IT 🟢  
MARKETING 🟢  
OPERATIONS 🟡

И система должна написать:

> ⚠️ Corner пока не готов к открытию.  
> Причины: оборудование и операционные стандарты.

То есть:

**процент выполнения задач ≠ готовность зоны.**

Это принципиально важно.

# 13. НАЙМ

Нужна простая система статусов найма:

`Need → Search → Interview → Offer → Hired → Onboarding → Working`

Раздел найма видит только CPO / Owner, плюс сотрудник, которому CPO явно выдал permission или назначил ответственным за конкретную вакансию (тогда видит только эту карточку, без зарплатных вилок, если они скрыты).

CPO видит:

- кого нужно нанять;
- на какую позицию;
- в какую зону;
- кто ответственный;
- текущий этап;
- когда человек должен выйти.

Не делать отдельную сложную HR-систему.

---

# 14. ЗАКУПКИ

Простая система закупок.

Каждая закупка:

- предмет;
- категория;
- зона;
- количество;
- стоимость;
- поставщик;
- ответственный;
- срок заказа;
- срок доставки;
- статус.

Статусы:

`Research → Quote → Approval → Ordered → In Transit → Delivered → Installed → Accepted`

Закупка может быть связана с задачей.

По умолчанию сотрудник **не видит** раздел закупок и **не видит цены**. Если он ответственный за связанную задачу — видит факт «нужно заказать X» / статус доставки без стоимости, поставщика и бюджета, пока CPO не откроет это permission.

# 15. ОБОРУДОВАНИЕ

Для критичного оборудования:

- название;
- зона;
- стоимость;
- поставщик;
- заказано;
- доставлено;
- установлено;
- протестировано;
- гарантия;
- Critical Yes/No.

Не делать из этого сложный ERP-модуль.

По умолчанию сотрудник не видит стоимость, поставщика и гарантийные документы. Видит оборудование только если оно связано с его задачей или CPO открыл доступ к зоне/разделу без финансовых полей.

# 17. УВЕДОМЛЕНИЯ

Система должна автоматически уведомлять пользователя:

# 22. UI / UX

Интерфейс должен быть:

- современным;
- минималистичным;
- визуально чистым;
- быстрым;
- понятным без инструкции;
- с хорошей типографикой;
- с понятными статусами;
- с аккуратными карточками;
- с хорошей визуализацией прогресса.

Не делать:

- перегруженные таблицы;
- 20 кнопок на экране;
- сложные формы;
- ненужные настройки;
- огромное количество меню;
- интерфейс в стиле старого ERP.

Главный принцип:

> **Progressive Disclosure — показывай пользователю только ту сложность, которая ему действительно нужна.**

### Общий визуальный язык (собрать из всех пяти)

- Светлая поверхность, почти белая, карточки белые, **огромный border-radius**.
- Пастельные заливки карточек: cream, mint, pink, lavender, peach, lemon — один акцент на карточку.
- Типографика: жирный крупный display для % и имени, мелкий серый лейбл.
- Навигация: sidebar-остров или icon-rail; активный пункт — цветной pill, не underline.
- Кнопки: pill. Primary тёмный или насыщенный; secondary outline.
- Прогресс: stacked bar, rounded bar, donut, горизонтальная task-bar с % — не таблицы.
- Аватары везде, где есть человек.
- Минимум линий-сеток; разделение = воздух и карточка.
- Light theme по умолчанию; dark — как в референсе 1, опционально.

# 26. БЕЗОПАСНОСТЬ

Обязательно:

- password hashing через стандартный auth provider;
- sessions;
- protected routes;
- role-based access + permissions поверх роли;
- database-level security (RLS): роль и permission проверяются на каждом запросе;
- пользователь не должен иметь возможность получить данные, к которым у него нет доступа — ни через UI, ни через API, ни через поиск, ни через создание задачи;
- скрытие в интерфейсе = скрытие в данных;
- CPO / Owner имеет полный доступ;
- сотрудник по умолчанию видит только свои задачи (ответственный / автор / участник) и выданные CPO разделы/зоны.

Не хранить пароли самостоятельно в базе.

# 28. ПРАВИЛО ПРОЦЕНТА

Процент проекта рассчитывается автоматически из задач.

Но сделать возможность учитывать вес задачи.

Например:

обычная задача = 1

критичная большая задача = 3

Это позволит не получать ситуацию:

> 90 маленьких задач выполнено = 90%

при этом главный строительный объект ещё не готов.

Формулу сделать простой и прозрачной.

# 32. ОСОБЕННО ВАЖНО

Не превращай этот проект в копию Notion, Jira или Monday.

Мы создаём **свой специализированный инструмент**.

Он должен ощущаться как:

> **Mission Control для запуска бизнеса**

а не как база данных.

CPO видит всю картину.

Сотрудник видит только то, что ему нужно сделать, плюс разделы/зоны, которые CPO явно открыл.

Роль даёт базовые права. Permission даёт точечный доступ. Не нужна информация для работы — её нет в интерфейсе и в API.

Сотрудник может самостоятельно создавать задачи.

CPO контролирует структуру, roadmap, людей и результат.

Система сама считает прогресс, показывает проблемы и помогает понять, успевает ли проект к открытию.

Начни с архитектуры и MVP.

Перед реализацией проверь структуру БД, permissions и основные пользовательские сценарии.

После этого создай рабочий web-прототип с реальной авторизацией, базой данных и основными экранами.

# Как довести модуль «Задачи» до уровня CRM X

Документ для владельца PHP-портала (модуль `tasks`: `module.json`, `routes.php`, `views/board.php`). Цель — повторить возможности CRM X, **не переписывая стек**: остаёмся на PHP + SQLite (или MySQL), меняем схему, правила и добавляем недостающие экраны и потоки.

Сравнение основано на присланных трёх файлах. `tasks.js`, `tasks.css`, схема БД и остальные модули портала мне не показаны — то, что в них уже есть, нужно свериться самому. Описание CRM X — в `docs/SERVICE.md`.

Пометки: 🔴 обязательно для «как у меня», 🟡 желательно, 🟢 по желанию. В конце — порядок работ (раздел 12).

---

## 0. Что в итоге должно получиться (целевая картина)

CRM X — не «доска задач», а **система управления запуском**: у каждой задачи есть код, поток, результат («готово когда»), зависимости, вес, критичный путь; по этим данным считается готовность проектов и вех; есть роли, бюджет, риски, контрагенты, журнал, Telegram-уведомления.

Ключевые отличия, которые нужно закрыть:

1. Богатая модель задачи (код, поток, результат, вес, critical path, зависимости, блок).
2. Жёсткие правила смены статусов.
3. Роли и видимость на уровне задачи, а не только проекта.
4. Журнал изменений и уведомления.
5. Аналитика: готовность, вехи, неделя, планёрка, проверка данных.
6. Каскад сроков и Roadmap.
7. Деньги, риски, контрагенты, Wiki (если нужны).
8. Надёжность: транзакции, права на каждый запрос, защита от гонок.

### 1.2. Новые таблицы 🔴

```sql
-- Зависимости: задача может стартовать только после закрытия других
CREATE TABLE task_dependencies (
  task_id       INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  depends_on_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  PRIMARY KEY (task_id, depends_on_id),
  CHECK (task_id <> depends_on_id)

-- Участники задачи (видят и работают, но не исполнители)
CREATE TABLE task_participants (

-- Несколько проектов на одну задачу (в CRM X task.zones[])
CREATE TABLE task_projects (
  task_id    INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,

  PRIMARY KEY (task_id, project_id)
);

-- Вложения (файлы на диске / в хранилище, в БД — только метаданные) 🔴

  size        INTEGER,

-- Реакции на комментарии
CREATE TABLE comment_reactions (
  comment_id INTEGER NOT NULL REFERENCES task_comments(id) ON DELETE CASCADE,

  PRIMARY KEY (comment_id, user_id, emoji)
);

-- Журнал изменений (пишет только сервер) 🔴
CREATE TABLE task_activity (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id    INTEGER,               -- без FK: журнал переживает удаление
  task_title TEXT NOT NULL,
  user_id    INTEGER NOT NULL REFERENCES users(id),
  kind       TEXT NOT NULL,         -- created|status|dates|assignee|edited|deleted|comment
  text       TEXT NOT NULL,
  days       INTEGER,               -- сдвиг срока в днях

  created_at TEXT NOT NULL

CREATE INDEX idx_activity_task ON task_activity(task_id, created_at);

-- Внутренние уведомления (колокольчик)
CREATE TABLE notices (

  task_id    INTEGER REFERENCES tasks(id) ON DELETE CASCADE,
  kind       TEXT,                  -- task_new|deadline|status|comment|broadcast
  text       TEXT NOT NULL,
  is_read    INTEGER DEFAULT 0,
  created_at TEXT NOT NULL,
  read_at    TEXT
);

-- Личные дела с напоминаниями (отдельно от задач)
CREATE TABLE todos (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  text        TEXT NOT NULL,
  done        INTEGER DEFAULT 0,
  remind_at   TEXT,                 -- UTC ISO
  repeat      TEXT DEFAULT 'none',  -- none|daily|weekdays|weekly
  reminded_at TEXT,
  task_id     INTEGER REFERENCES tasks(id) ON DELETE SET NULL,

  done_at     TEXT

```

## 2. Архитектура

### 2.1. Что изменить 🔴

| Сейчас | Нужно |
| --- | --- |
| Вся логика в одном `routes.php` (~600 строк) | Разнести: `lib/access.php` (права), `lib/task_rules.php` (правила статусов), `lib/activity.php` (журнал), `lib/notify.php` (уведомления), `lib/telegram.php`, `lib/schedule.php` (каскад), `lib/readiness.php` (аналитика) |

| Ответы `{"ok": false}` без причины | Единый формат: `{ok:false, error:"текст", code:"..."}` и корректные HTTP-коды (400/401/403/404/409/500) |

- Клиент должен получать **уже отфильтрованные** сервером данные (как `filterState` у меня): не отдавать чужие задачи, пароли, chat_id, финансы.

- Запросы одного браузера — по очереди (очередь), чтобы не перезатирать друг друга.

## 3. Статусы и правила переходов 🔴

### 3.1. Набор статусов

Привести к: `todo (Не начато · бэклог)` → `in_progress` → `review` → `done`; отдельная колонка **`blocked`** справа (не шаг пайплайна). Статус `on_hold` («отложено») заменить на `blocked` с причиной и сроком — в CRM X «отложено» = «заблокировано на срок».

### 3.2. Правила (проверять **на сервере** в одном месте — `canMoveStatus`)

1. **Зависимости.** В `in_progress`, `review`, `done` нельзя, пока есть незакрытые задачи из `task_dependencies`. Исключение: владелец и тот, у кого право `manage_users`. Ошибка: «Сначала закройте: GEN-02, GEN-03».
2. **Результат.** В `review` и `done` нельзя, если `result` пуст. Ошибка: «Заполните «готово когда»…».
3. **Блок.** В `blocked` нужны `block_until` (день/неделя/месяц/навсегда → конкретная дата или `forever`) и `block_reason`. Блок ставится **только в карточке**, не перетаскиванием.
4. При выходе из блока — вернуть `block_from_status` (или `todo`), очистить причину и срок.
5. Перетаскивание на доске идёт через те же правила (сейчас `update_status` принимает любой статус).

### 3.3. Флоу «сдать задачу»

`исполнитель` → заполняет «готово когда» → переносит в `review` → сервер проверяет (п.1–2) → пишет журнал → уведомляет **автора** («🟣 На проверке») → автор принимает: `done` (уведомление «🟢 Готово») или возвращает в `in_progress`.

### 3.4. Флоу «блок»

Исполнитель в карточке выбирает «Заблокировать» → срок + комментарий → статус `blocked`, автор получает «⛔ Заблокировано: причина» → в утренней рассылке и на планёрке задача попадает в «Что нужно для разблокировки».

## 4. Роли и видимость 🔴

### 4.1. Роли

| Роль | Что видит и может |
| --- | --- |
| Owner | Всё. Правит и удаляет любые задачи, управляет командой и деньгами |
| Управляющий | Все задачи своих проектов; ведёт статусы; правит сроки |
| Маркетолог | Поток BRAND & MARKETING в своих проектах + свои задачи |
| Сотрудник | Свои задачи, где участвует, и задачи подчинённых |

### 4.2. Функции (реализовать в `lib/access.php` и использовать везде)

- `can_see_task(user, task)` = Owner ∨ исполнитель ∨ автор ∨ участник ∨ руководитель исполнителя (рекурсивно по `user_managers`) ∨ поток открыт человеку (`user_streams`) ∨ управляющий проекта (для маркетолога — только задачи потока маркетинга).
- `can_work_task` (статус, чек-лист, комментарий, вложение, «готово когда», блок) — всё из «видеть», кроме чистых наблюдателей.
- `can_edit_task` (название, срок, вес, critical path, исполнитель) — Owner, `manage_users`, **автор**, управляющий проекта.
- `can_delete_task` — Owner любую; остальные только свои.
- `subordinates(user)` — рекурсивно.

### 4.3. Разделение полей при `update` 🔴

Сейчас любой участник проекта меняет **любое** поле. Нужно: если у пользователя только `can_work`, сервер принимает лишь «рабочие» поля: `status, result, block_reason, block_until, attachments, contacts`; остальные молча отбрасывает.

### 4.4. Фильтрация ответа 🔴

Сервер отдаёт: только видимые задачи; комментарии/чек-листы/журнал только по ним; уведомления и дела только свои; бюджет — только Owner и `finance`; пароли и `telegram_chat_id` не отдавать никому.

### 4.5. Закрыть дыры в текущем коде 🔴

- `todo_toggle`, `todo_update`, `todo_delete` — нет проверки доступа к задаче: любой вошедший меняет пункты чужих задач по номеру. Добавить проверку через `task_id` → `can_work_task`.
- `update` — не проверяет, что `title` не пуст.
- Добавить CSRF-токен на все POST (если его нет в ядре портала).
- Ограничение попыток входа: 5 ошибок / 15 минут на пару IP+логин, **хранить в БД или кэше**, не в памяти процесса.
- Сессия: подпись, срок жизни; смена пароля разлогинивает другие устройства (в токен кладётся отпечаток пароля).

## 5. Флоу задач (все сценарии)

### 5.1. Создание
1. Форма: название, проект(ы), поток, исполнитель, срок начала/конца, приоритет, «готово когда», critical path, зависимости, контрагенты.
2. Сервер: проверка прав на проект, уникальность `code` (если задан), даты (`start ≤ due`), проверка существования зависимостей (без циклов!), исполнитель — из участников проекта.
3. Запись в `tasks` + связи + журнал `created`.
4. Уведомление исполнителю (Telegram + колокольчик), если он не автор.
5. Идемпотентность: повтор запроса с тем же id не создаёт дубль.

### 5.2. Редактирование
- Полный набор полей — только `can_edit_task`. Каждое изменение статуса, срока, исполнителя, названия/результата пишется в журнал человеческим текстом («срок 05.10 → 12.10 (+7 дн)»).
- Смена исполнителя → уведомление новому.
- Смена срока → **каскад** (5.6).

### 5.3. Перенос по доске
Drag&drop → тот же API `update_status` → правила раздела 3 → при ошибке карточка возвращается назад с сообщением.

### 5.4. Удаление
Owner — любые; остальные свои. Каскадно: чистить `task_dependencies` (у зависимых убрать ссылку), комментарии, чек-лист, уведомления, ссылки в рисках и расходах (обнулять). Запись `deleted` в журнал (видна только Owner). Для задач с подзадачами — либо запретить, либо спросить «удалить с подзадачами» 🟡.

### 5.5. Подзадачи
Оставить ваши подзадачи (у меня их нет) — но добавить: пересчёт статуса родителя по подзадачам 🟡 и учёт подзадач в готовности.

### 5.6. Каскад сроков 🔴
Алгоритм (из `lib/schedule.ts`): при новых датах задачи идём по цепочке зависимых; если зависимая стартует раньше окончания предшественника — сдвигаем её **целиком** (длительность сохраняется) и идём дальше; раньше задачи не подтягиваем. Ограничение защиты от циклов (`guard` ≈ 10 000 итераций). UI: перед сохранением показать превью «сдвинутся N задач», кнопка «Применить». Сохранять по одной задаче, при первой ошибке остановиться и сообщить, сколько сохранено. Переносить перетаскиванием на Ганте (как у вас) → тот же превью.

### 5.7. Комментарии
Добавление, реакции-эмодзи (`comment_reactions`), запись в журнал (`comment`), уведомление исполнителю/автору 🟡. Удаление своих комментариев 🟡.

### 5.8. Чек-лист
Ваш `task_todos` оставить; добавить права `can_work_task`, порядок (`sort_order`), «отметить все».

### 5.9. Вложения 🔴
Файлы — в файловое хранилище (диск/S3), в БД только метаданные (`task_attachments`). Ограничить размер и типы. **Не хранить содержимое в БД/JSON** — у меня это узкое место, повторять не надо.

### 5.10. Контрагенты
Привязка контрагентов к задаче (`task_contacts`), с проверкой: привязывать можно только тех, кого пользователь видит; уже привязанные, но скрытые — сохраняются.

| **Профиль** | Смена пароля, подключение Telegram | 🔴 |
| **Wiki** | Страницы по проектам с видимостью | 🟢 |
| **⌘K палитра, справка** | Поиск, быстрые действия, онбординг | 🟢 |

### 6.2. Формулы (реализовать на сервере, чтобы не считать в JS по-разному)

- **Готовность** = Σ вес закрытых / Σ вес всех × 100 (вес: обычная 1, critical path 3). По проекту, по каждому потоку, по вехе.
- **Просрочена**: `status ≠ done` и `deadline < сегодня` (для «точечных» — по `start_date`).
- **Вехи проекта** (Демонтаж → Замер и планировка → Дизайн → Согласование → Ремонт → Оборудование → Команда → Soft launch → Открытие): собираются из задач по потоку и названию. Состояние: готово / в работе / просрочено / впереди.
- **Проверка данных**: у открытой задачи нет результата, исполнителя, срока или потока; начало позже конца; зависимость не найдена; задача стартует раньше окончания зависимости.
- **Риск** = вероятность(1–3) × влияние(1–3); ≥ 6 красный, ≥ 3 жёлтый.

## 10. Надёжность и эксплуатация 🔴

## 13. Чек-лист приёмки («у него как у меня», если…)

- [ ] У задачи есть код, поток, «готово когда», вес, critical path, зависимости.
- [ ] Нельзя перевести в работу/на проверку/в готово при незакрытых зависимостях (кроме владельца).
- [ ] Нельзя сдать без результата; блок без причины и срока невозможен.
- [ ] Сотрудник не видит чужие задачи; управляющий видит все задачи своих проектов; руководитель видит задачи подчинённых.
- [ ] Исполнитель не может менять срок и вес; автор и управляющий — могут.
- [ ] Любое изменение попадает в журнал; статусы «на проверке/готово/блок» приходят автору.
- [ ] Готовность проекта и потока считается автоматически и совпадает с ручным подсчётом на тестовых данных.
- [ ] Сдвиг срока переносит зависимые с превью; циклов зависимостей создать нельзя.
- [ ] Пароли хэшированы; смена пароля разлогинивает другие устройства; лимит попыток входа работает между запросами.
- [ ] Вложения не лежат в БД; есть бэкап и проверенное восстановление.
- [ ] Загрузка из шаблона Excel показывает ошибки построчно до записи и не создаёт дублей.
